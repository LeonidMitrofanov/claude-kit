# claude-kit — инструментарий работы с Claude Code

Шаблоны, скрипты и договорённости о том, как в проекте устроена работа через Claude Code:
делегирование задач отдельным сессиям и мост в Telegram к владельцу проекта.

Репозиторий подключается к проекту **git-подмодулем** в каталог `claude-kit/`.
Обновил в одном проекте, запушил — в остальных подтянул.

**Всё, что верно только для конкретного проекта, лежит в `project.conf` в корне
проекта и больше нигде** — номер группы Telegram, имя ключа в Keychain, номера тем,
имя оркестратора. Абсолютных путей в ките нет: корень проекта скрипты ищут сами.

Если ради нового проекта пришлось править что-то кроме `project.conf` — значит
привязка просочилась в код, и её надо вынести в настройки, а не тиражировать правку
по копиям кита. Ради этого кит и стал отдельным репозиторием.

## Раскладка: что чьё

```
<проект>/
├── claude-kit/        ← этот репозиторий, подмодуль. Только чтение для проекта
├── project.conf       ← настройки проекта. НЕ в ките: кит общий, настройки свои
├── .kit-state/        ← рабочее состояние моста. НЕ в ките и НЕ в git
├── tasks/             ← директории делегированных задач + REGISTRY.md
├── dialog/            ← стенограмма переписки с владельцем, наполняется приёмником
└── docs/              ← база знаний проекта
```

Три вещи вынесены из кита наружу намеренно:

| Что | Почему не в ките |
| --- | --- |
| `project.conf` | Кит общий для всех проектов, настройки у каждого свои. Внутри кита файл затрётся при обновлении подмодуля |
| `.kit-state/` | Состояние проекта, а не инструмента. Переустановка подмодуля (`rm -rf claude-kit` + `git submodule add`) его не задевает — а `offset` приёмника терять нельзя |
| `dialog/`, `tasks/`, `docs/` | Содержимое проекта. Кит — только скрипты |

## Модель работы

Одна главная сессия — **оркестратор** — общается с владельцем проекта и не делает
содержательную работу сама. Задачи она раздаёт отдельным сессиям Claude Code,
каждая из которых живёт в своём окне `tmux` и в своей директории `tasks/<задача>/`.

Так владелец в любой момент может обратиться к оркестратору и получить ответ сразу:
он не занят длинной работой, потому что длинную работу делают другие.

```
владелец ──▶ Telegram ──▶ оркестратор ──▶ сессия «задача-1» (tmux, tasks/задача-1/)
                              │
                              ├──▶ сессия «задача-2» (tmux, tasks/задача-2/)
                              └──▶ сессия «задача-3» (tmux, tasks/задача-3/)
```

Обратная связь идёт только к оркестратору, никогда напрямую к владельцу. Базовый канал —
файловый и работает всегда: сессия пишет в `OUTBOX.md` своей задачи и ведёт файл `STATUS`,
оркестратор читает их при обходе.

Поверх него может работать живой канал — `SendMessage` по имени сессии. Он есть,
**только если в окружении оркестратора заданы `CLAUDE_CODE_MESSAGING_SOCKET`
и `CLAUDE_CODE_MESSAGING_TOKEN`**: их поднимает среда запуска, а сессии, запущенные
оркестратором, наследуют их вместе с окружением. Голый `claude` в `tmux` их не создаёт —
тогда остаётся только файловый канал и опрос.

Схема спроектирована так, чтобы работать и без живого канала: он ускоряет обратную связь,
но ничего в устройстве не меняет.

### Мост в Telegram

| Файл | Зачем |
| --- | --- |
| `tg/config.sh` | Обвязка: пути, `tg_api`, токен из Keychain |
| `tg/kitconf.py` | Поиск корня проекта и чтение `project.conf` из Python |
| `tg/tg-poll.py` | Приёмник: `getUpdates` → файлы в `dialog/`. Живёт в своей сессии tmux |
| `tg/tg-wake.py` | Мгновенная доставка входящего в сессию оркестратора |
| `tg/tg-send.sh` | Отправка сообщения в тему, с файлом или ответом на сообщение |
| `tg/tg-edit.sh` | Правка своего отправленного сообщения (например правил темы) |
| `tg/tg-react.sh` | Реакция-индикатор состояния задачи |
| `tg/tg-pin.sh` | Закрепить или открепить |
| `tg/tg-link.sh` | Ссылка на сообщение в теме |
| `tg/tg-topic.sh` | Завести тему и узнать её идентификатор |
| `tg/tg-topic-icon.sh` | Поставить теме значок; `--list` показывает весь допустимый набор |
| `tg/tg-forward.sh` | Переслать сообщение группы в её же тему, сохранив вложение и авторство |
| `tg/test-poll.py` | Проверки разбора ответов и пересылок в приёмнике. Запуск без аргументов, код 1 при провале |

Настройки читают два разных языка, поэтому формат `project.conf` — подмножество shell:
`KEY="значение"`, комментарии на `#`, никаких подстановок. Bash берёт файл через `source`,
Python — тридцатью строками разбора в `tg/kitconf.py`. Обоснование выбора — в шапке
того же файла.

### Проверки

```bash
claude-kit/tg/test-poll.py                       # 12 проверок разбора входящих
for f in claude-kit/*.sh claude-kit/tg/*.sh; do bash -n "$f" || echo "СИНТАКСИС: $f"; done
for f in claude-kit/tg/*.py; do python3 -c 'import ast,sys; ast.parse(open(sys.argv[1],encoding="utf-8").read())' "$f" || echo "СИНТАКСИС: $f"; done
```

`test-poll.py` проверяет `quoted_ref` — разбор того, на что владелец ответил или
что переслал. Ошибки там не падают, а тихо портят смысл: приёмник допишет
в `dialog/` строку, где вопрос выглядит адресованным всему сообщению вместо
выделенной фразы, и оркестратор ответит не на то. Заметить это можно только
чтением переписки — поэтому и проверка.

Ожидание в наборе сравнивается со **строкой целиком**, а не по вхождению
подстроки: формат пометки читает человек, и меняться молча он не должен.

Проверки **не требуют ни настроек, ни проекта вокруг** — `tg-poll.py` читает
`project.conf` в `configure()`, которую зовёт `main()`, а не на уровне модуля.
Так кит остаётся пригодным к проверке, лёжа в репозитории один.

### Управление темами: чего нет в документации Bot API

Половина ограничений здесь не описана нигде, и каждое проверено дорого.

| Что | Как на самом деле |
| --- | --- |
| **Значок темы** | Не эмодзи в названии, а поле `icon_custom_emoji_id` метода `editForumTopic`. Набор закрытый — 112 штук, отдаёт `getForumTopicIconStickers`. Свой эмодзи подставить нельзя |
| **Поле `name` при смене значка** | **Не передавать.** Оно необязательное, и опущенное сохраняется. Передача «прежнего» названия выглядит безобиднее, но опаснее: промахнёшься в букве — название молча заменится |
| **Идентификаторы значков** | Не зашивать. `tg-topic-icon.sh` запрашивает набор каждый раз и ищет по самому эмодзи: вызов читается как «поставь 🎓», и список из 112 значений не устаревает молча |
| **Селектор варианта U+FE0F** | Telegram отдаёт часть значков как `⚡️`, а набирают их обычно как `⚡`. Сравнивать эмодзи надо после нормализации, иначе существующий значок просто не находится |
| **Закрепить тему** | Через Bot API **нельзя**: метода нет вовсе, `pinForumTopic` отвечает `Not Found`. Это клиентская операция, её делает человек |
| **Перечислить темы** | Тоже нельзя. Номер темы узнаётся только из входящего сообщения — приёмник копит их в `dialog/TOPICS.md` |

**Наборы эмодзи для значков тем и для реакций — разные, и проверяются порознь.**
`❓` Telegram принимает как значок темы, но отклоняет как реакцию на сообщение
(`REACTION_INVALID`). Поэтому «нужен ответ владельца» обозначается `🤔`.

### Рабочее состояние: `<проект>/.kit-state/`

Каталог создаётся сам и в git не попадает. Между проектами не переносится: содержимое
привязано к конкретному боту и конкретной живой сессии.

| Файл | Кто пишет | Что это |
| --- | --- | --- |
| `offset` | `tg-poll.py` | Номер последнего обработанного обновления. Потерять — значит перечитать историю заново или потерять часть сообщений |
| `orchestrator.sock` | оркестратор, при старте | Путь к unix-сокету своей сессии; по нему `tg-wake.py` доставляет сообщения мгновенно. Содержит PID, меняется при каждом перезапуске |
| `orchestrator.name` | оркестратор, при старте | Имя своей сессии из `ListAgents`; по нему `launch-session.sh` говорит делегированным сессиям, кому писать |

Оба указателя оркестратор записывает при старте — см. «Первым делом при старте»
в [ORCHESTRATOR.md](ORCHESTRATOR.md). `sweep.sh` чинит устаревший `orchestrator.sock`
сам, если видит расхождение с текущим окружением.

## Подключение к новому проекту

```bash
cd <корень проекта>
git submodule add <URL или путь к репозиторию кита> claude-kit
cp claude-kit/project.conf.example project.conf
$EDITOR project.conf                     # заполнить все <плейсхолдеры>
mkdir -p tasks dialog docs .kit-state
claude-kit/tg/kitconf.py                 # проверка: печатает корень, настройки, состояние
```

Дальше — [SETUP.md](SETUP.md): бот, группа, темы, токен в Keychain.

**Признак меры для этого кита:** новый проект подключается добавлением подмодуля
и правкой одного файла настроек. Понадобилось больше — значит в ките осталась
привязка к проекту, и чинить надо её, а не проект.

Пока репозиторий не выложен наружу, подмодуль можно добавить с локального пути
(`git submodule add <путь к каталогу этого репозитория> claude-kit`) — git это умеет.
Заменить локальный путь на URL потом: `git submodule set-url claude-kit <URL>`.

## Обновление кита

В проекте, где кит правится:

```bash
cd claude-kit
git switch main            # подмодуль по умолчанию стоит в detached HEAD
# правки
git commit -am "…" && git push
cd ..
git add claude-kit && git commit -m "кит: <что изменилось>"
```

В остальных проектах:

```bash
git submodule update --remote --merge claude-kit
git add claude-kit && git commit -m "кит: подтянул <что>"
```

Два коммита на одну правку — это не издержка, а суть: проект хранит **номер версии**
кита, а не его содержимое. Обновление кита в одном проекте не меняет остальные, пока
там не сделан второй коммит. Именно поэтому кит можно править, не боясь сломать
работающий проект.

**Правку кита ради одного проекта делать нельзя.** Понадобилось — значит не хватает
настройки: заведи ключ в `project.conf.example` и научи скрипт его читать.

## Как завести задачу

```bash
mkdir -p tasks/<slug>
cp claude-kit/SESSION-REQUEST.md tasks/<slug>/TASK.md
# заполнить все плейсхолдеры <...> в TASK.md
# внести строку в tasks/REGISTRY.md
claude-kit/launch-session.sh <slug>
```

Скрипт откажется запускаться, если `TASK.md` не заполнен или сессия с таким именем
уже есть в tmux. Правила он кладёт в `tasks/<slug>/CLAUDE.md`, подставив в них
имя оркестратора и корень проекта.

## Как посмотреть, что происходит

```bash
claude-kit/sweep.sh                              # общая картина
tmux attach -t <slug>                            # подключиться к сессии

# заглянуть, не подключаясь
tmux capture-pane -p -t "$(tmux list-panes -t '=<slug>' -F '#{pane_id}' | head -1)" | tail -40

tmux kill-session -t <slug>                      # закрыть
```

**`capture-pane` по имени сессии не работает** — отвечает «can't find pane» даже
с точным совпадением `=<slug>`. Нужен идентификатор пейна из `list-panes`. Ошибка
коварна тем, что выглядит как пустой экран, а не как сбой.

## Права делегированных сессий

Сессии запускаются в режиме `--permission-mode auto`. Выбор не произвольный — остальные
режимы проверены и не годятся:

| Режим | Что происходит |
| --- | --- |
| `bypassPermissions` | Запрещён управляемой политикой организации, флаг игнорируется |
| `manual` | Встаёт намертво на первом запросе — отвечать некому |
| `dontAsk` | Не спрашивает, а **отказывает**: сессия не может записать даже свой `STATUS` |
| `auto` | Рутина проходит, рискованное отклоняется классификатором |

`auto` выбран потому, что отказ сессия способна пережить: по правилам она пишет
об этом в `OUTBOX.md` и переходит в `Blocked`. Зависание пережить нельзя — оно молчит.

Границы при этом держатся не техникой, а текстом [RULES.md](RULES.md): классификатор
отсекает опасное вообще, а что именно можно трогать в этом проекте — знают только
правила. Поэтому раздел «Границы» там написан запретами, а задания формулируются узко.

## Бот Telegram: что действительно нужно

Обязателен один шаг: **сделать бота администратором группы**, с правом
«Управление темами» в придачу, если нужны темы.

Отключать «Group Privacy» у @BotFather **не требуется**. Проверено на двух ботах:
у обоих `can_read_all_group_messages` равно `false`, и оба видят все сообщения —
доступ даёт статус администратора, а не эта настройка. Не тратьте время на неё
и не считайте её причиной, если бот чего-то не видит: причина будет в правах.

## Требования

- `git` — кит подключается подмодулем
- `tmux` (проверено на 3.6b)
- `python3` — им пользуются и мост, и разбор настроек. Только стандартная библиотека,
  устанавливать нечего
- macOS `security` (Keychain) — там лежит токен бота
- `claude` CLI **версии 2.1.261 и выше** — нужны флаги `--name`, `--permission-mode`, `--add-dir`.
  Версия критична: на 2.1.224 unix-сокет обмена не создаётся вовсе, `SendMessage` не находит
  ни одного адресата, и живой канал молча не работает. Проверено дорогой ценой.
  Учти, что `claude` в `PATH` может быть старее бинаря из расширения VSCode —
  `launch-session.sh` поэтому сам выбирает самую свежую сборку на машине
- Разрешение `Bash(tmux:*)` в настройках оркестратора, иначе он не сможет ни запускать
  сессии, ни смотреть в них

Межсессионный обмен сообщениями **не требуется** — схема работает на файлах именно
потому, что его нет.

## Как выложить этот репозиторий на GitHub

Репозиторий создан локально: доступа на запись в GitHub с этой машины нет — ни `gh`,
ни ключа, ни токена. Что сделать владельцу, когда доступ появится:

```bash
# 1. Создать пустой репозиторий на GitHub (через веб или gh repo create),
#    БЕЗ README, .gitignore и лицензии — иначе истории разойдутся.
# 2. Привязать и отправить:
cd <каталог этого репозитория>
git remote add origin git@github.com:<аккаунт>/claude-kit.git
git push -u origin main
# 3. В каждом проекте заменить локальный путь подмодуля на URL:
cd <проект> && git submodule set-url claude-kit git@github.com:<аккаунт>/claude-kit.git
git submodule sync && git add .gitmodules claude-kit && git commit -m "кит: подмодуль по URL"
```

**Публичный или приватный — решает владелец.** Секретов в ките нет: токен живёт
в Keychain, номера чата и тем — в `project.conf`, который сюда не попадает. Так что
открыть его можно. Но текст кита описывает внутреннее устройство работы владельца
с проектами, и это довод не за, а против — вопрос вкуса, а не безопасности.
